# PieGame AI：内核可行性验证契约

本轮是团队内部、面向 Unity 的内核可行性验证，不是已接入现行游戏的 SDK。产品名 **PieGame AI**，程序集和命名空间 **`PieGame.AI.Kernel`**。

## 1. 依赖与宿主责任

- 内核源码在 `unity/Assets/PieGame.AI.Kernel/`；同一份源码由 `.NET` 工程通配符编译。无 Unity 引擎引用、无第三方依赖，不反向引用任何现有玩法程序集。
- ToyHost 仅在 `dotnet/PieGame.AI.Kernel.Tests/`，不是运行时包的一部分。
- 宿主负责裁剪视角、冻结载荷、编写提示与 Schema、解析和校验模型输出、在隔离快照上产生候选、选择哪些候选必须确认。
- 内核不认识库存、地点、角色、时段或骰子；字符串绑定是不透明权限主体标识，内核不解释其业务含义。
- `IStatePort.Read` 返回确定、脱离可变对象的状态字符串。`Write` 要么一次完整替换成功，要么抛异常且不改变状态；不允许先部分修改再抛异常。端口回调不得重入内核。

## 2. 原子性与并发边界

每个可变状态端口只由一个内核实例拥有。模型候选走 `Commit`，外部事件走 `Transact`，二者共用同一提交锁：先检查取消，再校验身份、会话代际和预期摘要，然后调用宿主写入并登记去重。`Reset` 也使用同一锁。

外部事务使用 `CaptureState()` 在同一次加锁中捕获代际、状态与摘要，提交时传入这个不可伪造的 `StateStamp`；不能只传摘要，否则重置到相同初态会让旧局事件穿透新局。字符串摘要使用严格 UTF-8，非法代理字符在写入前拒绝，不以替换字符悄悄丢失信息。

提供方等待、宿主解析和候选执行均不持有提交锁。此时外部事件可以提交，旧候选会因摘要变化被拒绝。

以下情况**不在原子性保障范围内**：绕过内核改状态、多个内核包装同一可变端口、宿主违反原子写入契约、宿主解析器修改实况。内核不提供磁盘事务或崩溃恢复，也不把“进程内锁”称为跨机器事务。

## 3. 取消与提交的线性化

| 观察点 | 回执 | 写入 |
| --- | --- | --- |
| 提交锁内首个取消检查已取消 | `cancelled` | 不写 |
| 提供方忽略取消后迟到返回 | `late_after_cancel` | 丢弃结果，不写 |
| 已越过取消检查，开始原子写入后取消 | `committed` | 不回滚；标注 `CancellationAfterCommit` |
| 回执返回后才取消 | 保持 `committed` | 已提交事实不变，标注可继续观察 |

宿主取消令牌不能撤销已经发生的提交。取消检查与之后写入之间存在不可分割的事务边界，不承诺在写入中途强行中断端口。

回执中的摘要描述该请求的事务基线和结果；拒绝提交不代表实况仍等于请求基线。比如 `stale_state` 正是其他事务已改变实况。需要查看当前状态时由宿主通过内核读取，不能把失败回执中的基线摘要误当“最新世界”。

## 4. 冻结、公开面与私有录制

`FrozenPayload` 复制传入字节，读取时再复制；绑定和指纹固定。宿主冻结后再改世界不会改变该请求发出的字节。

公开回执和 `Completed` 事件只提供请求 ID、机器状态码、摘要及取消标记，不附加原始输出、载荷、异常消息或世界快照。公开通道的订阅者应快速返回且不得抛异常；它们不是 Unity 主线程派发器。

包含冻结载荷、模型原文和世界快照的录制必须按**私有调试数据**保存，不应直接作为玩家可见轨迹。隐私测试只能证明测试宿主正确执行了裁剪边界，不能证明内核自动识别所有秘密。

## 5. 一次性确认能力

宿主仅在向用户展示候选并决定请求确认后调用 `IssueConfirmation`。返回的不透明随机字符串只保存在当前内核，绑定同一份不可变 `Preparation`：请求 ID、内核实例和会话代际、预期提交前摘要，以及候选身份（提案身份与候选后摘要）。不允许调用方自行构造授权对象或只传“同意=true”。比所需绑定更严格，同一请求重新准备出的对象也必须重新请求确认。

`Confirm` 与普通提交及外部事务共用锁，首查取消，再检查令牌与候选绑定。任何成功写入或换局都会清除全部待确认令牌，状态改走又改回也不能复用旧授权。重复确认返回 `confirmation_invalid`，普通已提交请求重复仍返回 `duplicate`；两者不是同一种语义。取消、伪造、错候选及无副作用的端口写失败不会提前消费有效授权。令牌属于宿主能力凭据，不应记录到公开回执或轨迹。

令牌不是用户身份认证系统。宿主负责“用户真正确认了已展示候选”，内核不能从一次方法调用推断真人意愿；宿主本身拿到令牌后仍是可信调用方。

## 6. 验证原则与后续范围

竞争用端口屏障复现，不以偶尔成功的压力测试替代边界证据；取消分别验证提交前、迟到和提交后；回放必须在校验通过前不修改实况。原有玩法的源码、黄金和研究统计是“不干扰”的证据，不是“已复用”的证据。

只有全部约定负例、黄金、统计和 Unity 编译通过后，才可以说“内核可行性验证通过”。要等现行游戏真正接入且原有黄金与统计不变，才能说“两个宿主共享同一内核”。本轮不迁移玩法、不做 Unity 桥、不做在线通用提供方，不改费用、预算或旧玩法代码。
