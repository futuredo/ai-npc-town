## 1. 已有输入：五项必须原样落入实现验收

下列五项视为用户已经确认的设计输入；实现仍须按本方案整体审批后进行，不能将它们扩大成未确认的新规则。

1. **默认生命周期**：已确认的约束持续到所属目标终止或玩家显式撤销，并覆盖该目标期间的后续玩家输入；模型重新理解、换一份计划、重规划或换提交入口都不能自动清除。技术上必须有可审计的 `objective_id` 和终止/撤销事件。
2. **保密默认范围**：保密标签默认保护“本次护送计划”，不是全镇所有秘密；“契约真相”是单独、单选的受保护主题，必须另行明确选择。不能把默认护送保密偷换成契约全面保密。
3. **`no_help` 边界**：允许买东西和普通询问；禁止托付/求助、招募/委托，以及当前梅伦“交付契约原件保管核验”的求助路径。它不是禁止所有社会接触，也不禁止独立居民行动。
4. **言契边界**：言契阻断玩家引起的后续转传；独立居民目击、独立流言和没有玩家根事件的社会消息不受该言契控制。不能因为文本相似就冻结整个居民社会。
5. **后续真实协议**：24 局为 `8 类 × 3 seed` 的后续真实协议建议。本任务真实请求数为 0；24 局、措辞、门槛和费用必须另批预注册并另获执行授权，不能由本方案或历史授权自动开始。

### 1.1 目标生命周期与到期边界

`DsPlanRun.Status` 的 `completed`、`failed`、`abandoned`、`needs_replan` 和取消提案都是**计划/运行状态**，不自动终止 `objective_id`。推荐的目标终止条件只有两类：

1. 系统依据玩家已确认的完成谓词明确写入 `objective_completed`；或
2. 玩家明确发起“结束目标”事务，写入 `objective_ended`。

玩家也可只撤销选定约束，写入 `constraints_revoked`：这只终止选定约束，不结束目标、不清空其他已确认约束；剩余标签不需要重新确认。结束目标则必须明确展示将结束该目标下的持续约束，不能借取消计划触发。

放弃旧计划、失败、重规划、取消提案和新建计划都继续使用同一个 `active_objective_id`。因此，放弃计划后新计划或直接 `Act` 仍必须经过同一 active ledger 检查，不能借新 `DsPlanRun` 或换入口绕过保密、`no_help`、only/required 等约束。

期限到达或目标路线失败时，分别记录约束/目标的 `expired`、`failed` 结果及完成谓词未满足状态；这只是结果记录，不是自动解除。到期后 deadline 本身可返回 `constraint_deadline_expired`，而保密、`no_help` 等持续约束仍保持生效，直至玩家明确结束目标/撤销约束；不能静默放宽，也不能把到期改算成功。**撤销和结束只影响未来，不回滚已经发生的披露、认知、盟友、物品或时间。**

### 2.2 必须正面处理的缺口

1. **约束没有世界身份**：当前 v1/v2 对象只挂在 `DsPlanRun`，读档、重规划和新计划无法从世界恢复同一契约。
2. **直接行动可绕过计划检查**：`DsExecutor.Prepare`、`ActAsync`、`RunStepAsync`、`RunWithProviderAsync` 和规则层测试入口都需要由同一个约束评估器覆盖，不能只禁用 Unity 按钮。
3. **`Partial confide` 已有真实副作用**：当前 `Confide` 先写入居民的 `plan` belief 和 `confided:*`，再判定梅伦/皮普是否实际愿意。允许的 Partial 应保留“已披露但未结盟”；违反保密或 `no_help` 时必须在写入前整体拒绝。
4. **居民 `tell` 目前不是玩家 tell**：现有 `AiTaskKind.AgentPlan` 的 `tell` 是居民夜间行动，玩家自由行动的动词白名单是 `Adjudicate`，没有通用的“玩家把某条认知告诉某居民”的 typed 入口。T4 应完整覆盖已经存在的 `AgentPlan/tell`，但不能把它冒充为玩家入口，也不能宣称当前已有通用玩家 tell。玩家主动 tell 是能力缺口，不作为本轮新增玩家动作/UI 的默认范围。
5. **来源链不足以做独立流言判定**：仅靠 `Source` 前缀、belief ID 中的 `@` 或文本相似度不能区分玩家根事件与独立目击。规则 10 必须增加结构化来源字段；旧来源无法证明时不能默认放行。
6. **目标 ID 尚不存在**：`DsPlanRun` 有 goal 字符串，但直接 `ActAsync` 没有 objective 绑定。要满足“覆盖后续输入”，必须增加宿主维护的当前目标上下文，或给每个玩家提交带不可伪造的 objective ID；建议先采用单会话一个 `active_objective_id`，减少公开 API 组合爆炸。

## 3. 最小可执行语义

### 3.1 约束不是模型台词

模型可在独立的约束捕获阶段返回候选标签，例如：

```json
{
  "proposal_id": "cp-17",
  "objective_id": "obj-escort-01",
  "kind": "keep_private",
  "protected_topics": ["escort_plan"],
  "allowed_actors": [],
  "scope": ["player_actions", "plan_and_replan", "player_origin_tell"],
  "deadline": null,
  "public_label": "保密：本次护送计划；不向居民披露；持续至目标终止或撤销",
  "source_input_id": "input-42",
  "source_span": "谁也别告诉",
  "completion_predicate": "objective_termination"
}
```

该对象是草稿，不进世界、不改变规则、不消耗时间、不改变骰子、不产生 `confirmed_event_id`。玩家必须在可见界面确认、修改或拒绝；低置信度和高置信度均不能自动激活。玩家也可以从结构化控件直接选择标签，不必依赖模型理解。

实现上建议让约束捕获是独立的 `DsConstraintProposal` 协议，而不是向当前 `ds_plan_v1` 隐式塞字段。这样旧计划 Schema、旧 Plan 黄金和“模型提出计划”仍能独立审计；如果以后给模型增加捕获任务，应使用新的任务/Schema 版本，不让原文片段成为执行权限。

### 3.2 `PlayerConstraint` 数据形态

下面是 rules-10 的最小持久结构。字段名是实现建议，稳定 ID 和取值白名单比 C# 属性名更重要。

```text
PlayerConstraint
  id                    string              // 世界内唯一
  schema_version        "player-constraint-v1"
  revision              int                 // 同一目标的单调修订号
  objective_id          string              // 不从 goal 文案推导
  issuer                "player"
  kind                  keep_private | no_help | only_helper |
                        require_helper | deadline
  protected_topics      string[]            // escort_plan / pact_truth 等白名单
  allowed_actors        string[]            // 稳定居民 ID；空集合不是“任意”
  required_actor         string?
  deadline              DsMoment?           // 结构化 day + phase，不比较中文
  scope                 player_actions | plan_and_replan | player_origin_tell
  status                active | satisfied | revoked | expired | failed
  confirmed_event_id    string
  effective_from        DsMoment
  revoked_event_id      string?
  source_input_id       string?
  source_span            string?
  public_label           string
  completion_predicate   stable predicate ID
```

实际集合不能由调用方持有可变 `List` 直接暴露。建议在 `DsWorld` 中增加不可变语义的 ledger 投影：

```text
PlayerConstraintLedger
  ledger_revision
  active_objective_id?
  constraints[]
  events[]              // confirmed / revoked / satisfied / expired / failed
```

`events` 是本地回放和审计所需的结构化记录，不把完整原始玩家输入或居民私有状态送给模型。确认/撤销是世界事务：不花玩法时间、不掷骰、不执行托付动作，但会更新世界版本、ledger revision 和快照哈希，使旧计划、旧分支和在途提交变为 stale。撤销本身不是违规候选的零写入例外，而是玩家明确授权的合法状态变化。

### 3.3 语义白名单

| 标签 | 最小规则效果 | 明确不扩张为 |
| --- | --- | --- |
| `keep_private(escort_plan, allowed=[])` | 禁止玩家直接 `confide`、玩家来源的计划披露和其后续转传 | 不保证他人原本不知道；不抹除旧认知；不保护契约真相 |
| `keep_private(pact_truth, allowed=...)` | 仅在玩家另选该标签时，阻断会披露契约真相的 show/give/confide/tell 效果 | 不由默认护送保密自动启用；普通 give 不因名字相似自动判定泄密 |
| `no_help` | 禁止 `request_help`/`confide`、招募/委托和梅伦契约原件保管求助路径 | 不禁 buy、普通询问、非求助 show、独立居民行动或独立流言；show 若披露受保护主题，仍由主题标签检查 |
| `only_helper(actor)` | 求助/托付对象只能是该居民；可独行，不要求真的得到帮助 | 不把“只找”解释成禁止所有与其他居民的普通接触 |
| `require_helper(actor)` | 禁止换帮手；完成谓词必须看到该居民实际 `ally:*`，不能用摘要、Partial、show 或 give 替代 | 不保证对方一定同意；不把交件视为结盟 |
| `deadline(moment, predicate)` | 预演和实际提交使用同一结构化时钟；到期未满足则 failed，不自动延长 | 不提供必胜承诺；不把合法骰失败改成规则成功 |

多个已确认标签取交集。确认阶段如果发现 `no_help + require_helper(pip)` 等结构冲突，整组拒绝并给出冲突原因，不静默删除其中一个。`pact_truth` 是独立单选主题；如果产品希望同时保护两个主题，应由玩家分别确认两个明确标签，不能由“保密”一词隐式扩展。

### 3.4 目标生命周期

- `objective_id` 由宿主在开始一个玩家目标时生成，不能由模型从 `goal` 字符串自报。
- 同一 `objective_id` 的首案、修正、重规划、计划步骤和后续直接输入读取同一 active ledger。
- `DsPlanRun` 必须保存 `objective_id` 与确认时的 `ledger_revision`；`Accept`、分支选择和每一步都重新核对。
- 只有明确完成谓词或玩家明确结束目标才生成目标终止事件；单独撤销约束只产生所选约束的撤销事件，其他标签及目标保持有效。两者都更新修订号并使旧在途请求失效；计划放弃、失败、重规划、取消提案不生成目标终止事件。
- 放弃/失败/到期后的新计划和直接输入继续复用同一 `objective_id` 与 ledger；已执行披露不回滚。只有明确结束后，玩家才可新建目标；新目标不能自动继承旧目标的约束。

## 4. 所有提交点的统一检查方案

约束检查必须是一个纯函数式、无副作用的 `DsConstraintEvaluator`，输入为冻结的世界候选、当前 ledger、候选动作/计划和 objective context，输出结构化 `DsConstraintDecision`。规则执行前先检查；规则执行后只在候选世界中写入；Commit 前再核对原快照、ledger revision 和候选身份。中文文案只是展示，稳定 `DsReason.Code/Entity` 才是断言依据。

这里要区分两层门禁，不能声称所有自由文本拒绝都发生在模型 Provider 之前：

1. **结构化层**：计划 `Accept`、分支选择、冻结计划步骤、`RunStepAsync`/`RunPlanStepAsync`、直接结构化调用和已有 Kernel 提交，已经有候选或结构化动作，不需要额外 Provider；必须在移动、跨夜、额外 Provider、耗时、掷骰和规则副作用前检查 objective/revision 与约束。
2. **自由文本层**：`ActAsync` 可以先发送一次角色裁剪、冻结且有界的模型请求，把玩家文本解析为一个合法候选；解析完成后，必须在规则副作用、时间、掷骰和提交前运行同一 evaluator。模型提案本身违规要分账为模型提案失败；最终规则拦截是安全通过，不能倒写成模型遵守，也不能宣称理解玩家文本前零模型调用。

| 提交点 | 必须检查 | 违规时允许的变化 |
| --- | --- | --- |
| 模型捕获标签 | 只产生 `DsConstraintProposal`；不写世界 | 提议记录可留在本地 trace，不能出现 active/confirmed 状态 |
| 玩家确认标签 | 对象、主题、范围、期限、冲突和 objective 校验；生成 confirmed 事件 | 只写约束事务、版本/哈希和审计事件；不花时间、不掷骰、不托付 |
| 计划生成 | 计划/重规划只读 active ledger；不因模型文本再登记或修改约束 | 仅在 PlanReport/trace 中报告缺口；世界不变 |
| 计划采用 `Accept` | 选中的 branch 独立重验；检查 `objective_id`、ledger revision、所有 active steps；旧草稿不可替换 | 不登记 `AcceptedRequestIds`，不启动夜间/移动/Provider/步骤 |
| 每个计划步骤 | 在移动、跨夜、耗时、掷骰、结构化 RunStep 前冻结步骤与约束 revision，并再次检查 | `StepResult` 为 `void/failed`，无 request ID、receipt、时间、骰序和世界差异 |
| 直接结构化行动 | `RunStepAsync`、`RunPlanStepAsync`、`RunWithProviderAsync` 和 `DsExecutor.Prepare` 都必须进入同一终闸 | 不因调用方是固定 Provider 就跳过约束；同样返回稳定拒绝码 |
| 自由行动 | `ActAsync` 旧路径和 Kernel 的 `IDsActionTransaction` handler 使用相同评估；自由文本允许一次合法裁剪模型提案，解析后在规则副作用前检查；Kernel committed 只能表示候选已原子写入，不替代约束语义 | 模型提案违规另记模型失败；规则拒绝在候选层发生，不写 belief/ally/物品/时间；不因 UI 入口不同放行 |
| `confide` 的 Partial | 在 `Confide` 写 belief、`confided:*`、请求标记和耗时前检查 disclosure/request_help；允许的 Partial 才能保留“已披露未结盟” | 违反约束时整次拒绝，零写入；不得把 Partial 降级成“没说出口” |
| 玩家触发 tell | 当前没有该入口；本轮不新增玩家动作/UI，不以缺口阻塞现有路径的规则安全 | 不得用居民 `AgentPlan/tell` 代替；未来若独立新增，必须复用本 evaluator 和来源约束 |
| 居民夜间 `AgentPlan/tell` | T4 必须完整覆盖：先解析整组 share 的来源链；带玩家 root 的受保护消息逐条检查；混合受保护/独立消息整次原子拒绝 | 不新增听者 belief、关系增益或已传话日志；独立且可证的居民流言仍按原规则继续 |
| 撤销/过期/目标终止 | 这是合法 ledger 事务；旧候选和旧确认均 stale；未来候选按新状态检查 | 不删除已存在的认知、流言、盟友或物品后果 |

### 4.1 `PlayerTell` 的明确缺口与可选未来范围

当前代码没有通用玩家 tell API。本轮不因约束设计增加新的玩家动作或 UI；现有入口先完成硬拒绝和来源链治理。若未来另立独立任务增加窄的、结构化 Core 入口，可采用：

```text
PlayerTell(objective_id, target_actor_id, belief_id[], reason)
```

它只接受玩家此刻持有/可合法引用的认知 ID，经过 `DsExecutor` 候选事务提交；不接受模型自报的世界事实，不接受任意文本编译成 `share`。无论未来是否增加该入口，都必须继承本 evaluator、objective/revision 检查和来源约束；在该入口不存在期间，T4 不宣称覆盖玩家主动 tell，但必须覆盖现有 `AgentPlan/tell`。

## 5. 居民来源链与独立流言

### 5.1 新字段

在 rules-10 的 `DsBelief` 增加并写入快照：

```text
root_event_id          // 玩家动作或独立亲历事件的不可变根事件
origin_kind            player_action | resident_observation | resident_action | external
origin_player_objective string?
parent_belief_id       string?
topic_id               escort_plan | pact_truth | event:* | other whitelist
```

现有 `RootId/RootOwner/Hops/Source` 继续保留用于旧回放/显示兼容，但 rules-10 的保密判定只使用结构化字段。新 `confide` 产生 `origin_kind=player_action` 的根事件；后续合法转述复制 `root_event_id`、`origin_player_objective` 和 `topic_id`，不允许模型通过换 belief ID、改 `Source` 或改文本洗白来源。

### 5.2 Tell 的原子性

`ShareBeliefs` 在写入前先完成整组预检。若候选包含任一受保护玩家根消息与任何超范围接收者，整次 tell 拒绝；不能像当前普通 Partial 一样先写一半再报告。对于不涉及受保护玩家根的独立目击流言，仍按现有最多两跳、根去重、回传拒绝和关系效果执行。来源无法证明属于独立事件时，不得用“文本看起来像独立流言”放行。

这只控制**玩家引起的转传**。它不让皮普、玛尔妲或其他居民变成道德完美，也不冻结独立调查、独立目击和原有社会冲突。

### 5.3 旧来源迁移边界

来源枚举必须按**因果根**而不是最后一个观察者或显示文本归类。新世界初始化和实际规则事件从明确的结构化来源开始：真正独立的居民目击/居民行动才写入 `resident_observation`/`resident_action`；而居民亲眼看到玩家 `give`、`show`、`confide` 等动作所产生的认知，根仍是 `origin_kind=player_action`，复制 `root_event_id`、`origin_player_objective` 和主题，观察者只是该玩家事件的见证者，不能把它洗白成 `resident_observation`。`DsContent` 的初始认知也必须逐条登记明确根来源，不能给所有初始消息套一个默认枚举；不能用显示文本或 `Source=seen:event` 前缀临时猜测。旧 `DsBelief` 只有字符串来源，无法为所有历史认知补齐玩家根事件。启用 active 新保密标签时：

- 能由现有结构确定属于新目标玩家根的认知，才纳入阻断链；
- 旧来源无法证明时，必须显式迁移/校验并向玩家提示，返回 `constraint_legacy_origin_unproven` 或 `constraint_migration_required`；不能用默认文本猜来源，也不能为补绿而把全部旧独立流言一律误拦成受保护消息或全社会禁言；
- 不删除、不重写已经存在的听者认知；
- 历史 rules-6/7/8/9 replay 只保留原字节并作为跨版本拒绝的档案证据；当前代码不提供多规则版本运行时，不能把这些历史帧表述为可在旧规则宿主中各自运行。
