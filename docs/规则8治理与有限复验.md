## 1. 三项治理与版本边界

1. **岗哨范围**：`ContextBuilder.CurrentPlanRequirements` 只解释已裁剪视角。`guards_here` 始终指玩家当前地点；被关状态下，只有当前在王城且眼前有卫兵才提示“此地不能立即 rescue”。龙骨岗有岗哨不再推出异地王城禁止救援；仍须到场观察、接受实际回执，不补发隐藏岗位或 NPC 私有信任。
2. **结构反馈**：`DsPlanRun.RejectedFeedback` 在无预演分支且 `schema_invalid` 时，转发已有 `PlanReport.Issues`（无报告才取 `ValidationIssues`），过滤空项、最多 **3 条、每条 140 字符**；首条兼作 reason，附“未执行草稿”警示。不回显原始坏输出，不把预演异地状态当现状。这不是所有失败分支都新增 issues。
3. **规律限次**：`DsRules.Adjudicate` 用 `Distinct(StringComparer.Ordinal)`；同一次行动同 ID 的支持/阻碍只计一次，大小写不归一。最终源码在读取 laws 时先去重，再剔除未知/未获知规律，避免残留重复 ID 抑制客观阻碍；不是依靠模型不重复。

规则显式升为 `dragonsleep-rules-8`，是规则/提示协议升级，**不是 rules-6/7 向后兼容或新旧行为全等**。旧工件不改写版本、不重录覆盖；当前同版本正例另存。三项代码位置均在 `unity/Assets/Town.Core/Dragonsleep/`。

## 6. 三个真实失败：请求、规则、时间分账

三局均 `abandoned / plan_call_limit`、各6次 Plan，末态第3天黄昏，`actual_with_mother=false / final_dawn=false`；没补推进终局。

### Solo seed3：实际救援骰失败，不是 schema 错误

- `L/solo-seed-3/plan-calls.jsonl:1 → S1-1` 原始第一步是 **`op=act, verb=wait, until=第3天·黄昏`**，实际仅耗2点，不是 `op=wait` 的跨时段等待；随后很早上龙骨岗露天等候。`rule-events.jsonl:3 → S1-R9` 在第3天清晨换岗捕获，显示概率0.25、骰0.12，原件回执确实写入关押。
- `plan-calls:2/3 → S1-15/17` 虽被接受，实际 `action-traces.jsonl:14/15 → S1-16/18` 分别在第3天清晨/正午报 `place_guarded`，`no_change / applied=false / time_cost=0`，无掷骰。移动王城已发生；不得把接受或预演成功写成救援成功。
- `plan-calls:4 → S1-19` 等至第3天黄昏；`action-traces:16 → S1-20` 原始实际 rescue 引用 `laws=[law_fear_noise]`、difficulty0.5、narration“按计划：安静”，最终难度 **0.36**，原生 roll **0.1105**，`roll_failed`。回执 `committed / applied=true / time_cost=2`，随机计数1→2、spent0→2、写入 `rescue_failed`，小烬仍关王城。
- `plan-calls:5/6 → S1-21/22` 余2点仍提 `rescue@castle → hide@skull_hill → wait至第4天清晨`；预演步骤2报“第三个黎明已至，来不及执行”，均未接受。最后原始回包仍是这三步，不是新执行。末态玩家王城、spent2、roll_counter2；18循环，接受ID仅 `S1-1/15/17/19`。

### Pip seed1 / seed3：恢复提案失败，没实际 rescue

- 两局 `action-traces.jsonl:1 → S1-2` 实际结盟；`:11 → S1-12` 是皮普向总管转述，不是玩家越权托付。`rule-events.jsonl:2 → S1-R11` 第3天黄昏入龙骨岗时被捕，概率0.15，显示骰分别0.15 / 0.12；显示精度不能证明 seed1 原骰恰等于阈值。
- 两局 `plan-calls:2 → S1-15` 原始回包 `rescue@castle → hide@skull_hill`，局部可执行但未包含等母亲，`reaches_goal=false`，没有确认执行。seed1 的 `:3/5 → S1-16/18`、seed3 的 `:3/4/5 → S1-16/17/18` 又重复 `confide pip@docks`，预演步骤2“皮普不在这里”；送回模型的反馈屏蔽了异地位置推断，不把预演发现当当前事实。
- 最后两局 `plan-calls:6 → S1-19` 原始均仅 `rescue@castle, laws=[law_fear_noise]`；**可执行但不覆盖归巢**，非已接受救援。seed1 `:4 → S1-17` 亦如此。两局接受ID均仅 `[S1-1]`，actual action 文件没有 rescue；11循环、玩家仍龙骨岗、spent0、roll_counter1、小烬仍关王城。

## 7. 反馈是否送达、重复规律是否出现

27份真实回包全部 `failure=null / issues=[]`：15份预演覆盖目标、7份预演不可行、5份仅局部可执行。**schema_invalid=0，因而没有真实请求携带本轮新增的详细结构 issues**，不能写成“模型收到新 issues 后修好了深夜”。27份原始计划无 `op=wait` 的深夜/Night终点，也未再出现旧批“先等第4天清晨再救”的恢复路线；有限未出现不证明因果或全面防住。

岗哨修正文案确实出现在发给提供方的 perception：Solo `S1-15` 和两局 Pip `S1-15…19` 均明确龙骨岗不代表王城；Solo `S1-17/19` 明确当前王城眼前限制。三局末段请求都有适用的 `deadline_recovery`，Pip 还收到“已经答应 pip，不必重复 confide”，但仍重复托付/局部救援；提示送达不等于遵从。对应 `provider_prompt.sections[perception]` 与落盘 perception 已核对相同。

扫描27份**原始** Plan 回包所有 steps：重复 laws **0**；16条实际 Adjudicate 请求也无重复。故此真实批次没有重复规律攻击样本，不能把“模型未重复”冒充确定性防线已受真实对抗检验。限次与未知规律的边界靠规则代码及专项离线测试负责，不把重复规律当合法收益。
