# 分支与协作规范

## 长期分支

| 分支 | 用途 | 合入方式 |
| --- | --- | --- |
| `main` | 默认分支，保存已验证的阶段基线 | 从 `develop` 提 PR，使用 merge commit 保留两条长期分支的共同历史 |
| `develop` | 日常开发集成分支 | 从功能或修复分支提 PR，可使用 squash merge |

初始化时两条分支指向同一提交。项目仍处于原型阶段，`main` 不表示已经完成完整游戏验收。

## 短期分支

- `feature/<主题>`：从 `develop` 创建，例如 `feature/npc-dialogue`。
- `fix/<主题>`：从 `develop` 创建，例如 `fix/knowledge-source`。
- `docs/<主题>`：文档修改，例如 `docs/event-design`。
- `hotfix/<主题>`：仅在稳定基线需要紧急修复时从 `main` 创建；合入 `main` 后，再把 `main` 合回 `develop`。

功能分支合入后删除，`main` 和 `develop` 长期保留。不对长期分支强制推送，不重写已共享的提交。

## 日常流程

```bash
git switch develop
git pull --ff-only
git switch -c feature/npc-dialogue
# 完成修改后：检查 diff，运行与改动相关的验证
dotnet test dotnet/Town.sln --configuration Release
git add <本次修改的文件>
git commit -m "实现居民对话请求与执行反馈"
git push -u origin feature/npc-dialogue
gh pr create --base develop
```

提交信息使用中文，描述具体行为变化。PR 写清问题、改动、验证和尚未覆盖的范围。多人或多个开发任务并行时分别使用分支；需要同时操作同一仓库时使用独立 worktree，避免互相切换分支和覆盖文件。

## 验证与保护

GitHub Actions 的 `core-tests` 检查在推送 `main`、`develop` 及向这两个分支提出 PR 时运行，也支持手动触发。检查复用 Unity 内的 `Town.Core` 源码，使用 .NET 8 运行现有 NUnit 测试。

该检查覆盖核心逻辑，不覆盖 Unity 完整构建、场景渲染、寻路体验或模型服务。涉及这些内容时，PR 中补充对应验证结果。

长期分支的目标保护规则为：通过 PR 合入、`core-tests` 通过且分支保持最新、解决所有讨论、禁止强推和删除。单人阶段不要求其他人审批，避免无法完成自己的 PR；后续有协作者时再增加审批人数。远端是否能强制执行以 GitHub 仓库设置为准。

## Unity 与本地数据

- 提交 `Assets` 及对应 `.meta`、`Packages` 和 `ProjectSettings`。
- 不提交 `Library`、`Temp`、`Logs`、构建产物和 .NET `bin/obj`。
- API Key 使用本地环境变量或被忽略的 `.env`，示例仅提供无密钥的 `.env.example`。
- 同一个场景或 Prefab 尽量由一人编辑；合并后检查引用及 `.meta` GUID。
- 阶段验收后再建立版本标签；初始化提交不提前标记为正式发布版本。
