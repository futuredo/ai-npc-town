# 雏龙归巢：M3 真实规划实验

日期：2026-11-09。模型 `gpt-6-luna`，规则 `dragonsleep-rules-5`。本报告区分首轮、提示适配复验和固定失败状态探针，不把它们合成一个准确率。

## 结论与验收

本轮完成有界真实规划实验与一轮提示适配，**尚不能把模型规划判为通过切片验收**。原始提示首个计划在冻结集为 0/14、新措辞集为 0/10；适配后冻结集为 10/14（71.4%），仍低于 80%。离线基线在这两个集合上都是 100% 可执行，因此“严格高于基线”的原门槛在当前集合上无法满足；本轮没有降低或改写门槛。

| 验收项 | 本轮结果 | 判定 |
| --- | --- | --- |
| 首个计划 ≥80% 且高于基线 | 适配冻结 10/14，基线 14/14；适配新措辞 10/10，基线 10/10 | 未通过 |
| 三类失败各 ≥10 例、可补救计划 ≥70% | 90 局实际失败 76/62/15；可补救重规划 59%、69.9%、91.7% | 前两类未通过 |
| 无效引用不被确认执行 | 所有整局中 0 个违规计划被接受；探针只提案、不执行 | 本批通过 |
| 回执一致 100% | 适配冻结 90/90 局记录一致，其中 74 局有实际步骤；250 成功、138 失败、376 作废步骤均通过记录检查 | Core 记录通过，M4 UI 未验 |
| 三种求助各 ≥3 种子 | 每种 10 种子，盟友与消息传播有差异 | 有限机制通过 |
| 归巢、新约、铁笼救回、未竟可达 | 本轮 208 项离线回归包含 M1 结局脚本；真实整局另见下表 | 离线回归通过，不等于 AI 通关验收 |
| 等待超过 5 秒有可取消提示 | 首轮及适配均有 >5 秒请求，延迟完整记录 | M4 待实现 |
| 真人小测 | 未进行 | M5 待做 |

## 冻结边界与方法

- `PlanCases.cs` 未修改，与 `e4103dc` 文件一致；14 例冻结集指纹仍为 `bfac3c38bc8b20fd156211217eda55385a4f7875abe37f1075fcb8026ea66147`。新措辞沿用原来的 10 例。
- 先跑离线 `--plan --seeds=10`，再跑两批 `--seeds=2 --live`。提示适配后另批复验；已看过的新措辞复验不再称为未见过的盲测。
- `--seeds` 是**世界掷骰种子**，不是 API 采样种子；每批首个计划集只跑一遍，不能把 10 种子写成首个计划重复 10 遍。
- 所有联网请求只用于 `AiTaskKind.Plan`。居民、GM、计划步骤与世界推进仍离线；模型拿到玩家冻结的 `TaskPerceptionView` 与系统生成的失败上下文。
- 保持单并发、输出 ≤768 tokens、请求体在联网前强制检查 ≤12 KiB、无 HTTP 自动重试、不切换模型。CLI 只有 `--live` 才读密钥并联网。失败也计入原账本。
- 整局最多 10 次计划调用；首个计划不可行立即停止该局的计划执行，不在相同状态偷偷重抽；执行失败触发显式重规划，连续两次新计划不可行就放弃。这与服务故障重试不同，每次均有记录。
- 社会取舍的盟友/总管知情在计划完成或放弃时记录；随后照常推进到终局计算结局。两者测量时点不同，未把尚未发生的夜间传话提前算入。
- 可执行率沿用冻结判据：默认分支通过结构、已知引用及固定成功掷骰的规则试运行。它**不等于达成归巢目标**，也不保证真实掷骰、居民移动后仍成功。另报告试运行团聚和实际结局。

## 适配内容

首轮主要问题是协议与动作含义不完整：模型把“小烬”、`pip：皮普`、`skull_hill：龙骨岗` 当 ID；把 `lead` 当“直接送到目的地”、`rescue` 当“从藏身处接出”、`confide` 当“问路线”，并产生冗长分支。

本轮只修改 `ContextBuilder` 的 Plan 提示：

1. 明确英文 ID、`whelp`、地点与对象字段的区别。
2. 说明诱引/喂食的信任与消耗、藏匿不等于跟随、救援成功自动跟随、已跟随不重复带上；提醒求助条件。
3. `act/wait` 自带先移动，减少多余 `go`；已明确的取舍不强造分支。
4. 提醒总输出预算 768 tokens，缩短目标、概述、目的和引用，优先不超过 8 步；协议上限仍为 14 步。

没有改变动作规则、校验器、离线基线或冻结案例。剩余典型错误包括食物消耗后再使用、把 `whelp` 填入 `item`，以及把“接回雏龙”误用为 `take`。

## 三类失败与固定状态探针

完整模型整局与固定探针分开报告。探针来自本轮离线 90 局产生的实际失败记录，按记录顺序选取每类前 10 个可补救快照及前 3 个死局，不按模型输出选样。

有效探针文件：`.local/m3/recovery-fixtures-v2.json`，SHA-256：

```
9a469aac706913dedd2c3f2cdd7daad61720acfb1d6998efda5de9964be6ee71
```

完整世界快照和死局标签仅用于本地恢复、校验及分类，**不发送模型**；恢复后仍走 `PlanAsync` 重建玩家感知。每个探针只请求一次、不确认执行。33/33 已离线逐条对照原始提案文本及可执行性一致；基线在可补救部分为 30/30，在 3 个死局均不可行。

探针只补足固定状态下的重规划测量，不表示模型自己产生了此前行动，也不是新增世界、独立随机大样本或完整补救成功率。前置条件组主要来自低信任梅伦，场景覆盖有限。

### 重复失败做法的解释边界

对重规划记录比较失败步骤与新默认分支的动词、对象、物品和地点，忽略步骤 ID 与取舍标签。这个计数只是“同一动作再次出现”，不自动判错：掷骰失败后可以再试，先补条件再托付也合理。

人工核对的失败样本包括：
- `full:bonded_docks::seed=1 / S1-15`：救援成功会自动跟随，计划却再 `lead`，试运行拒绝“小烬已经跟着你了”。
- 同局 `S1-19`：得知城门有岗后尝试 `lure guards`，对象 `guards` 不在可操作对象内，引用校验拦截。
- `full:informed::seed=2 / S1-10`：再次诱引、喂食后仍不足以解除受惊状态，继续 `lead` 被拒。
- `perturb_stale:informed::seed=1 / S1-19`：雏龙实际已被商人带走，但玩家只知道它不见了；新计划继续去码头搜索被判不可行。这是已标记死局，不计入可补救成功率。

这些样本表明提示中的“不要重复”不足以解决状态推理，不能仅凭新 plan ID 判断模型已经换了办法。

## 无效引用、回执与等待

无效引用会在确认执行之前拦截。统计分别给出违规计划数、违规引用条数与被接受计划数；同一计划可能有多条无效引用。卫兵相关审阅同时检查未知岗位引用，不把已知的 `law_guards_dusk` 算作越权。

回执一致性检查的是 `DsPlanRun` 状态、步骤回执与确认记录。首轮整局没有真正执行步骤，空结果的一致不能当成功证据。**Unity 计划面板尚未实现，UI 与回执 100% 一致仍待 M4 验收。**

规划延迟按完整 trace 计算，中位数与 P95 使用 nearest-rank；首个计划和重规划都计入。首轮已有多次超过 5 秒，M4 必须做“正在规划”、取消和取消后的过期结果拒绝，不能因适配后变快而省略。
