## 一、对现有计划（策划大纲 v0.1）的评估

**总体判断：方向对、边界清楚，可以作为起点；但它是「策划方向稿」，还不能直接开工排期。**

### 做得好的地方
1. 选题和手册推荐一致（第 01 项「知识边界记忆」），研究问题收敛成一句话，可验证。
2. 「世界事实 / NPC 相信的 / NPC 说的」三层分离、「模型提出，程序裁决」，这两个架构判断是对的，也是这个题目和「多人聊天小镇」拉开差距的地方。
3. 0 容忍项（越权改状态、重复发物品、旧局污染）写得很具体，工程上可测。
4. 对参考案例的边界说明很克制，汇报时不会被追问「你是不是照搬」。

### 主要问题
| # | 问题 | 影响 | 本次处理 |
| --- | --- | --- | --- |

- **已确认：你一人 + Claude 协作。** 任务约 23 人日，但其中约 60% 是写代码、写用例、写模板和文档，可以由 Claude 承担；你的实际投入约 12—14 天，留出约 1 周给调手感、试玩和意外。可行。

## 二、角色分工（按「职责线」分，可映射到 1—3 人）

| 职责线 | 代号 | 负责内容 |
| --- | --- | --- |
| 策划 / 内容 | **P** | 角色卡、事件与命题表、台词与快捷话题、引导、试玩组织、汇报叙事 |
| 客户端 | **C** | Unity 场景、NavMesh、日程表现、交互、UI、调试面板、存档 |
| AI 系统 | **A** | Town.Core：认知、检索、提示、模型接入、校验、执行、日志回放 |
| 评估 | **T** | 用例集、跑批工具、指标统计、试玩问卷与数据分析 |

### 你和 Claude 怎么分

| | **你负责** | **Claude 负责** |
| --- | --- | --- |
| 决策 | 范围取舍、每周 M 验收是否通过、砍什么 | 给出选项与推荐，不替你拍板 |
| P 策划 | 定稿角色性格与口吻、判断「好不好玩」、组织试玩和访谈 | 起草角色卡、命题表、模板台词、引导文案、问卷，你改 |
| C 客户端 | 在 Unity 编辑器里摆场景、调相机与手感、看画面、录屏 | 写全部 MonoBehaviour、UI 脚本、调试面板；用编辑器脚本自动生成灰盒场景和 NavMesh，减少你手动搭的量 |
| A AI 系统 | 申请模型 API Key 并配到本地环境变量（Claude 不碰密钥）、读模型输出判断角色像不像 | 写 Town.Core 全部代码：认知、检索、提示组装、模型接入、校验、执行、日志回放，并配单元测试 |
| T 评估 | 审用例是否合理、解读结果、写结论 | 写用例集、跑批工具、统计脚本和图表；在命令行跑测试与跑批 |
| 交付 | 汇报叙事、答辩 | 报告初稿、图表、实验数据整理 |

**Claude 做不到的：** 直接操作 Unity 编辑器界面、看游戏实时画面（需要你截图或描述）、替你登录账号或填写密钥、代你找同事试玩。

### 协作方式
- **一个任务一轮对话：** 你说「做 W1 周一的任务」，Claude 写代码 → 跑 dotnet 测试 → 告诉你需要在 Unity 里点什么、看什么。
- **代码先过测试再进 Unity：** Core 逻辑全部在命令行验证，你在 Unity 里只验证表现和手感。
- **每天收工：** 你把在 Unity 里遇到的问题（报错文本、截图）给 Claude，下一轮先修。
- **建议立即 `git init`**，每完成一个任务提交一次，出问题可回退。

## 六、落后时的砍需求顺序（从先砍到后砍）

1. 次日回访 → 改成收尾界面里一段文字
2. 单槽存档 → 只保留「重置本局」
3. 阿禾的 NPC 间闲聊传播 → 只保留「玩家告知」这一条传播路径

**不能砍：** 三层分离、请求版本校验、引用校验、0 容忍项测试、至少 3 人试玩。
